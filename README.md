## Multi-Agent Pattern: Orchestrator-Worker

```
[Orchestrator]
     │
     ├── Phase 1 → [DataScout]       → output/portfolio_summary.json
     │                                  (reads: data/portfolio.csv)
     │
     ├── Phase 2 → [RatioAnalyst]    → output/ratios.json
     │                                  (reads: portfolio_summary.json
     │                                          data/transactions.json)
     │
     ├── Phase 3 → [PolicyRAG]       → output/policy_context.json
     │                                  (reads: ratios.json + policy chunks)
     │
     ├── Phase 4 → [ReportWriter]    → output/credit_memo.md
     │                                  (reads: all three JSON files)
     │
     └── Phase 5 → [Evaluator v1]   → scores credit_memo.md
                   [ReportWriter v2] → credit_memo_v2.md (with feedback)
                   [Evaluator v2]   → scores credit_memo_v2.md
                                       → eval_scores.json (delta)
```

## Enterprise Readiness Assessment

**Status: NOT YET production-ready. Three conditions must be met:**

1. **SR 11-7 Model Validation**: The Ratio Analyst constitutes a model
   under US Federal Reserve SR 11-7 guidance (and equivalent COBAC standards).
   An independent validator must review its logic before it touches real credit data.

2. **Data Quality Gate**: The pipeline currently accepts any CSV without schema
   validation. Production requires a data contract layer that verifies required
   fields and refuses to proceed on malformed input.

3. **Human Sign-Off Requirement**: Per COBAC credit risk guidelines and ECOA,
   a licensed credit analyst must review and sign the final memo before it
   reaches the Risk Committee. The AI is a productivity tool, not a decision maker.

## What Broke / What I'd Change

See `output/eval_scores.json` for the evaluator's specific improvement suggestions.

Key observations from log analysis (`logs/agent_calls.jsonl`):
- PolicyRAG uses the most tokens (retrieving and reasoning over policy sections)
- RatioAnalyst has the highest latency (complex ratio computation + data loading)
- Evaluator v1 tends to score ~1 point higher than warranted (auto-inflation bias)
- The improvement loop reliably improves the 2 lowest-scoring dimensions

What I'd change for production:
1. Replace simulated RAG with actual vector DB (ChromaDB or pgvector)
2. Add async fan-out for DataScout + PAR computation
3. Add data schema validation before Phase 1
4. Use a DIFFERENT model for the evaluator (same model = grader bias)
